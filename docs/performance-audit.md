Performance and resource audit of the server/data layer, on branch `t3/audit-server-data-performance`.

Estimates below come from code paths, not production measurements. No database was contacted. Line numbers refer to the resulting implementation.

Implemented findings:

- `src/lib/auth.ts:19`: layout authentication and `getCurrentPlayer` independently verified claims using separate Supabase clients. Shared request-scoped claims memoization removes one verification/client construction on an authenticated layout render. A full navigation now has one proxy verification and one server-render verification, rather than up to three combined. With asymmetric signing and warm JWKS these are local checks; symmetric keys or unavailable WebCrypto cause the SDK to contact Auth. Proxy refresh and both `ALLOWED_EMAILS` checks remain intact. `getCurrentPlayer` already deduplicated its player lookup; it was not an N+1 across layout/page.
- `src/lib/queries.ts:422`: practice picker and training plan computed the same weaknesses with different limits. Cached the complete ranking per player, then sliced per caller. Removes two DB queries per practice-page render (five recommendation queries become three), without sharing results between requests.
- `src/lib/queries.ts:246`: target summaries and spread loaded every target-practice dart, twice for an unfiltered profile. Grouped by target, intended ring, landing and hit in SQL; cached with primitive player/range keys. One shared query on the all-time profile; result size grows with distinct combinations rather than lifetime darts. Preserves separate repeated targets in different rings.
- `src/lib/queries.ts:447`: training loaded every X01 visit but used only start scores 41–120. Filters before aggregation and returns at most two range totals. Legacy dart attempts still participate in the same greatest-of-turn-and-dart calculation.
- `src/lib/queries.ts:124`: profile stats made a dependent bot-game query with a lifetime game-ID parameter list. A correlated `NOT EXISTS` now supplies bot eligibility in the existing match query: one fewer round trip and no growing parameter list. Independent cricket fetching now starts with the other stats queries.
- `src/lib/queries.ts:569`: stats and achievements queried/replayed the same cricket history on all-time, all-scope profiles. Request-scoped caching shares the query and replay for identical scope/range keys: one fewer query and replay. Together with target and bot-query deduplication this removes three DB queries per default profile render.
- `src/lib/queries.ts:306`: fatigue fetched every timed dart and ran a correlated session-minimum subquery per dart, then repeatedly filtered the result in JavaScript. SQL computes one minimum per relevant game and groups into at most seven time buckets; bust darts remain in the denominator with zero points. - `src/lib/queries.ts:326`: ghost model loaded every dart in the date range and then fetched independent volume totals serially. Two aggregate queries now run concurrently and return two rows. Preserves sample thresholds, fallback rating, and null-target double-attempt behavior.
- `src/lib/queries.ts:46`, `src/lib/queries.ts:238`, `src/lib/queries.ts:399`, `src/app/online-actions.ts:60`: game relations fetched full player profiles and room actions fetched unused room-dart columns. - `src/lib/persist-game.ts:72`: ranked saves issued one rating upsert plus one history insert per participant. Sorted advisory locks, the shared before-period, transaction boundaries, duplicate-game guard and 1,000-dart batches are preserved.
- `src/app/online-actions.ts:77`: leave/rematch reordered members with per-player UPDATEs. One CASE UPDATE replaces the loop and skips unchanged rows. Saves up to two statements on a lobby leave and three on a four-player rematch. All mutation operations retain the original exclusive room-row lock.

Remaining findings and deliberate deferrals:

- `src/lib/queries.ts:73`, `src/lib/queries.ts:479`, `src/lib/queries.ts:569`: all-time scoring, achievements and cricket remain proportional to lifetime turns/darts. Achievements fetch all visits and darts; cricket must replay useful marks. History/chart output is also intentionally unbounded in `practiceHistory`, `ratingHistory` and `headToHead` (`:180`, `:226`, `:388`). Truncation would change results. Persistent aggregate tables or per-player caches need explicit invalidation for all participants, bots, online saves, date windows and UTC-day rollover. SQL aggregate reductions above do not eliminate underlying history scans. No production query plans were available to justify more speculative indexes.
- `src/app/players/[id]/page.tsx:47`, `src/lib/queries.ts:19`: viewing one's own profile still fetches the same player once by auth user ID and once by profile ID (one redundant small DB read). The page currently starts both lookups in parallel for every player; resolving auth first to skip the self-read would serialize other-player navigations. A shared player loader can address this with a broader data-access refactor.
- `src/app/online-actions.ts:58`: every dart/undo loads and replays the current room game's history, bounded at 5,000 entries. This is O(D) per action and O(D²) over a game. A materialized authoritative engine state/version could reduce it, but requires coordinated undo, replay, aggregate-entry and conflict handling. Kept the current row-lock semantics.
- `src/lib/use-room.ts:95`, `src/lib/use-room.ts:266`, `drizzle/0002_online_rooms.sql:117`: focus/visibility/subscription events can request an additional snapshot while one is in flight; multi-row membership updates emit multiple room events. Each accepted refresh transfers the complete active dart history. The existing dirty-refresh flag protects events arriving during a read; removing it indiscriminately risks missing state. Room timestamps are updated on transitions/saves, not on each throw. Per-dart sync is already incremental and event driven; no periodic polling was found.
- `src/lib/game-store.ts:61`: local game writes serialize the full active history and pending saves to localStorage; snapshot reads cache parsed JSON. Cost is O(D) synchronous serialization per dart, O(D²) across a game. Deferred IndexedDB/incremental persistence to preserve the offline queue and durability contract. `plan-store` has parsed snapshot caching and no network activity; `sync.ts:14` already coalesces in-flight flushes and keeps retryable saves.

Frontend-owner handoff (resolved items marked):

- **Fixed:** devices now autosave by seat order (first seat after 20 s, each next one 4 s later), so the first save's realtime update cancels the others. Original finding: `src/app/r/[code]/online-game.tsx:89`: every connected participant schedules `finishRoomGame` and refreshes on finish. Up to four clients can submit the same save, serially acquire the room lock, touch/broadcast and invalidate pages. Idempotency prevents duplicate games/ratings, but not repeated requests. Consider one active saver with a delayed fallback for other devices so disconnects do not lose saves.
- **Fixed in the counter:** it refreshes only when a save went through. Original finding: `src/app/play/counter.tsx:118`, `src/components/sync-pending.tsx:17`: action revalidation is followed by explicit `router.refresh`; counter refreshes even when no save succeeded. Both callers may also attach refresh callbacks to the same shared flush. Potential one or more additional RSC fetch/render passes per flush. Coordinate a single refresh owner and gate it on successful saves.
